# M1 Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `energy_mcp` without auth: a seeded synthetic world, four tools, the `reports://` resource and the `investigate_alert` prompt, with strict argument handling, served over stdio and Streamable HTTP on protocol revisions 2025-11-25 and 2026-07-28. Plus lesson 01.

**Architecture:** `world.py` builds the same world from a seed. `server.py` registers tools as `Tool.from_function(...)` objects, so their published `inputSchema` can say `additionalProperties: false`, and passes them to `MCPServer(tools=..., middleware=[guard])`. `guard.py` is an SDK middleware that runs before the SDK's own handling. It returns `-32602` for an unknown tool or prompt, validates tool arguments strictly against the published `inputSchema` (jsonschema, Draft 2020-12), and validates prompt arguments. `__main__.py` is the CLI (`python -m energy_mcp --transport stdio|http`). Tests use the SDK `Client` in-process for most checks, and real subprocesses for the transport checks.

**Tech Stack:** Python 3.12, mcp 2.3.0 (`MCPServer`, `Client`, `mcp_types`), pydantic 2 (output models), jsonschema 4.26.0, anyio's pytest plugin (`@pytest.mark.anyio`), pytest 9.2.0.

**Spec:** [`docs/plan.md`](../../plan.md), milestone 1, plus [`CLAUDE.md`](../../../CLAUDE.md). The SDK facts below were checked on the installed `mcp` 2.3.0 by throwaway spikes on 2026-11-22. The spec rules were read from the 2025-11-25 and 2026-07-28 pages for tools, prompts and resources.

### Task 4: The guard: strict tool arguments, unknown tool (SRV-04)

**Files:**

**Interfaces:**
- Consumes: the `Tool` objects from Task 3 (their `.name`, `.parameters`).
- Produces: `class ArgumentGuard` with `__init__(self, tool_schemas: Mapping[str, Mapping[str, Any]], prompt_args: Mapping[str, tuple[frozenset[str], frozenset[str]]] = {})`. The tuple is `(required, allowed)`; Task 5 fills `prompt_args`. Also `async __call__(self, ctx, call_next)`. Validators are built once per tool (`Draft202012Validator`).
  - `tools/call`, name not in `tool_schemas`: raise `MCPError(code=INVALID_PARAMS, message=f"Unknown tool: {name}")`.
  - `arguments` present but not a dict: raise `MCPError(INVALID_PARAMS, "Invalid params: arguments must be an object")`. A missing `arguments` counts as `{}`.
  - Schema errors: return `CallToolResult(content=[TextContent(type="text", text=msg)], is_error=True)`, where `msg = f"Invalid arguments for tool {name}: " + "; ".join(sorted(parts))`. Each part has the form `<path>: <what>`. `path` is the error's `absolute_path` joined by `.`, or `(root)`. `what` is:
    - for `required`: `missing required property 'meter_id'`, one part per missing name;
    - for `additionalProperties`: `unexpected property 'zzz'`, one part per extra key;
    - for `anyOf` (pydantic publishes each optional parameter as `anyOf: [X, {"type": "null"}]`): describe the sub-error from `error.context` whose schema is not `{"type": "null"}`, so `status` reports its `enum`, not `anyOf`;
    - otherwise: `must satisfy {validator} {json.dumps(validator_value)}`, for example `limit: must satisfy minimum 1` or `limit: must satisfy type "integer"`.
  - Every other method passes through unchanged.

- Edit the `SRV-04` row's text only if the implementation forces a change; the row was added in Task 1.
